## プロジェクト一言
家具が玄関→部屋まで「運び込めるか」を判定するアプリ（名前=Odoriba/踊り場）。
核心の主張: 既存は「浮いた剛体」しか見ないが、実際は人が運ぶ＝人体も通路を占有する。
「家具だけなら通るが、人が運ぶと踊り場で回れない」を、通る/通らない＋あと何cm＋上限サイズで出す。

## 何が動くか（Phase 2 の到達点）
1. 仮想L字階段の判定: `phase2_lstair.py`（環境=SDF直方体の合併、可搬性オラクル、RRT-Connect）
   - 出力: 通る/通らない、ボトルネック掃引で「あと何cm」、上限サイズ二分探索（幅/長さ）
   - 可視化: `phase2_lstair_3d.py`(plotly HTML)
2. （欠番）数値から仮想階段を組むデモ `virtual_demo.py` は 2026-10-23 に削除。`stair_report.py --width ...` で同じ寸法指定ができる
3. スキャン取り込み系（iPhone LiDAR / Scaniverse で撮ったOBJ）:
   - `scan_ingest.py`: 読み込み（`load_scan_zup`）・単位推定・穴埋め・水密化ロジック（`to_free_space_voxel`）
   - `measure_stairs.py`: 階段スキャンから寸法計測（蹴上げ/踏み面/幅/段数/天井）
   - `scan_sections.py`: 経路に沿って、段ごとの「壁から壁の幅」「手すり込みの幅」「天井の高さ」を測る（幅はこちらを使う）
   - 第1世代の可視化デモ（`scan_demo` / `scan_combined` / `scan_babylon` / `scan_furniture`）は 2026-10-23 に削除。下の 7 が後継
4. あなたの階段への答えレポート: `stair_report.py`
   - `python stair_report.py --measure-stair stair.obj --quick`（掃引のみ・速い）
5. 定番家具カタログ一斉判定: `catalog.py`（重い。普段は1家具ずつでよい）
6. 運搬者の体は人型（`human_figure.py`）。描画も判定も人型。円柱は `phase2_lstair.BODY_MODEL="cylinder"` で比較用に残してある
7. **スキャンした空間をそのまま判定**（型の階段なしで、玄関→部屋の経路全体）:
   - `scan_space.py`: メッシュ→距離場（2cm格子）・床・中心線。水密化不要。撮れた床の範囲で区切る
   - `scan_plan.py`: 中心線に沿ったRRTとボトルネック掃引。一番厳しい点（何に当たったか）も返す
   - `route_env.py`: 検証用の合成経路（玄関・廊下・曲がり角・ドア）。`python route_env.py` で正解と突き合わせ
   - 使い方: `sp = ScanSpace(mesh, 自由空間の1点); sp.build_centerline(出発点, 目的地); scan_plan.sweep_capacity(sp, num_carriers=2)`
     （ScanSpaceはオラクルの `outer` にそのまま渡せる。obstacles=None、floor_fn=sp.floor_fn）
   - `scan_picker.py`: **ブラウザで床に出発点・目的地を置き、家具の候補をまとめて判定する画面**（2026-11-24 に一括判定を組み込んだ）。
     `python scan_picker.py <スキャン.obj または Scaniverse の zip>` → http://localhost:8001（`--route` で検証用の合成経路）。
     空間は判定のときに出発点の上を起点にして作る（約1分、以後は使い回す）
     - 流れ: 床をクリックして出発点・目的地を置く → 入力欄に候補を1行1件で書く（`名前, 幅, 奥行, 高さ, 重さ`。重さは省ける）→「判定する」→ 候補ごとの ○/△/× と理由の表 → 行の「3Dで見る」で一番狭い所の様子
     - 判定と文言は `scan_candidates.py` と同じもの（`judge_candidates`、`row_parts`）。1件あたり十数秒〜1分かかり、終わった候補から表に出る。候補は12件まで
     - 読めない行が1つでもあれば判定しない（候補が黙って減らないように）
     - 「3Dで見る」は、その候補を表と同じ向き・重さで判定し直して作る（十数秒〜1分）。水平でも持てない重さの候補には出ない
     - 判定は1件ずつ直列に動く（家具の寸法をモジュールの変数で差し替えているため）
   - `scan_viewer.py`: 判定結果の3D（中心線を余裕で色分け、一番狭い所の家具と人を赤く、当たった点に印）

8. **重さの判定**（2026-10-13）: `python stair_report.py --furniture 80 45 60 --weight 70 --quick`
   - 重さを与えると、下側の人の負担が上限（業者40kg／自分たち25kg、仮値）を超えない傾きまでしか許さない
   - 出力: 何度傾ければ通るか、そのとき下側の人に何kgかかるか、業者・自分たちそれぞれ何kgまで運べるか
   - 重さを与えなければ従来どおり（傾き上限55度固定）
   - **候補の一括判定でも重さを扱える**（2026-11-24）: `python scan_candidates.py <スキャン> --item 冷蔵庫 70 65 180 100 --carried-by diy`
     - 重さは `--item` の5つ目（CSVなら5列目）。省いてよい。`--carried-by` は `mover`（業者、既定）か `diy`（自分たち）
     - 重さを書かない候補: ○と△の行に「業者なら◯kgまで / 自分たちなら◯kgまで」が付く（商品ページの重さと見比べる）
     - 重さを書いた候補: その重さで傾けられる角度までで判定。重さのせいで入らなければ × 「重すぎる」と、何kgまでなら入るか
     - 仕組み: `scan_plan.judge(tilt_detail=True)` が掃引を傾きの上限なしで1回だけ回し、上限ごとの結果（`bottleneck_by_tilt`）を返す。オラクルは変えていない
9. **回帰テスト**: `python -m pytest tests`（phase2/ で、約1分）。L字・折り返し・回りの掃引の基準値を固定

## 重要な設計判断（触る前に知っておくこと）
- **状態空間に人の姿勢を足さない**。6DOF(位置3+クォータニオン4)のまま、衝突判定器を
  可搬性オラクルに差し替える（`feasible=collisionFree ∧ ∃h carriable`）。ここが新規性。
- 環境はSDF（「あと何cm」が副産物で出る）。家具は表面サンプル点で近似。
- RRTのSE(3)距離の回転重みは `w_rot`。**L字では60**（0.4だと90°旋回のエッジ検証が
  粗くて壁を貫通する誤判定。過去のバグ）。`rrt_connect(..., w_rot=...)` で渡す。
- スキャンは**撮ったまま環境として使う**（`scan_space`）。手すり・扉などの意味は認識しない。
  外すものは外して撮る前提で、出力は「どこで何cm足りないか」と当たった点の座標。
  水密化はせず、出発点からの塗りつぶし＋撮れた床の範囲で内外を決める。
  寸法から型の階段を組む方式（`measure_stairs`）も残っている。
- 「あと何cm」は測る経路と掃引の刻みで変わる（L字で手引きの中心線 −29cm / 自動の中心線 約−13cm、
  刻みによる揺れ約2cm）。発表の数字の扱いは未決定（`docs/decisions.md`）。
